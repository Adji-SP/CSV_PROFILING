# ESP32-S3 managed firmware runtime

This project is the stable, initially USB-flashed ESP32 program. It owns ESP-IDF
startup, Wi-Fi, OTA download, status reporting, and rollback. Product behavior is
provided by the `device-app` Cargo dependency.

```text
src/main.rs
├── crates/application-api     shared AppContext and application contract
├── crates/wifi-manager        single owner of modem/Wi-Fi/reconnection
├── crates/ota-runtime         registration, polling, streaming OTA, SHA-256
└── applications/default-app   application used for initial USB provisioning
```

Every managed dashboard build copies this runtime to an isolated build workspace
and replaces only the `device-app` dependency with the uploaded application. The
result is still one statically linked ESP-IDF application image.

## Configure, build, and flash initially

On Windows, the repository-root helper guides you through the process:

```powershell
.\flash-esp32.ps1 -CheckOnly  # Check installed prerequisites; no build or device access
.\flash-esp32.ps1 -BuildOnly  # Prompt for network settings, build, and generate OTA .bin
.\flash-esp32.ps1             # Build, then ask before USB flashing and monitoring
```

Run these from the repository root in PowerShell. The helper loads the Visual
Studio and ESP Rust environments automatically. It prompts for a password without
echoing it, and restores the calling shell's environment afterward. Credentials
are still embedded in compiled firmware, so treat the firmware and build cache
as sensitive. The helper does not save a credentials file or install tools.
If needed, override `-PythonPath`, `-TargetDir`, or `-ToolsDir`. Cache directories
must be dedicated, short absolute paths without spaces. Defaults reuse
`F:\csv-esp`, `F:\csv-idf`, and `D:\Python\python.exe` when available.
Without F:, caches are placed on the project's drive. To flash, confirm your
board is an ESP32-S3 with at least 4 MiB flash and type the requested confirmation
for its COM port. Failed builds stop before flashing; cancellation keeps the
build outputs without writing to the device.

For manual operation, follow the steps below.

Use the ESP Rust environment and build-time values. `DEVICE_ID` is optional; when
absent the runtime derives a stable ID from the station MAC address.

```powershell
$env:WIFI_SSID="your-ssid"
$env:WIFI_PASS="your-password"
$env:OTA_SERVER_URL="http://192.168.1.5:7000"
$env:DEVICE_NAME="Sensor node"
cargo +esp build --release --target xtensa-esp32s3-espidf --locked
```

Building does not write anything to the board. Before flashing, review
`partitions.csv` against the board's actual flash layout: this example requires
at least 4 MiB. Do not use `localhost` in `OTA_SERVER_URL`.

For initial USB flashing, explicitly use the bootloader generated by this build.
Its rollback setting matters; a generic bootloader is not a substitute. The
following PowerShell command uses the same output location as Cargo:

```powershell
$targetDir = if ($env:CARGO_TARGET_DIR) { $env:CARGO_TARGET_DIR } else { "target" }
$releaseDir = Join-Path $targetDir "xtensa-esp32s3-espidf/release"
# Run only after checking the board and supplying real network settings above.
espflash flash --chip esp32s3 --monitor `
    --bootloader "$releaseDir/bootloader.bin" `
    --partition-table partitions.csv --target-app-partition ota_0 `
    "$releaseDir/esp32-rust-ota-client"
```

Prefer this explicit flash command over the basic `cargo run` runner, which does
not specify the rollback-enabled bootloader. Initial USB flashing replaces the
application and partition layout; it is not an OTA deployment.

## Windows build environment

Open a **Developer PowerShell for VS 2022** terminal with the C++ Build Tools and
Windows SDK installed. Load the ESP Rust environment and make sure `python`
resolves to a real base Python installation, not the Windows Store shortcut or
the Flask virtual environment. Install the linker helper once:

```powershell
cargo +stable install ldproxy --locked
. "$env:USERPROFILE/export-esp.ps1"
```

ESP-IDF's Windows build paths must be short. For example, the verified local
build used the following paths (adjust the drive and Python path for your PC):

```powershell
$env:PATH = "D:\Python;" + $env:PATH
$env:CARGO_TARGET_DIR = "F:\csv-esp"
$env:ESP_IDF_TOOLS_INSTALL_DIR = "custom:F:\csv-idf"
# Set your WIFI_SSID, WIFI_PASS, and OTA_SERVER_URL, then:
cargo +esp build --release --target xtensa-esp32s3-espidf --locked
```

Run these commands from this example's directory. `.cargo/config.toml` explicitly
preserves the project root when using an external target directory, loads
`sdkconfig.defaults`, and copies `partitions.csv` into ESP-IDF's generated build
project. Without this, a successful compile can still use the wrong partition
and rollback settings. The first build downloads ESP-IDF and its tools; retain
the cache for subsequent builds.

To produce an **application-only OTA image**, without flashing a device:

```powershell
$targetDir = if ($env:CARGO_TARGET_DIR) { $env:CARGO_TARGET_DIR } else { "target" }
$releaseDir = Join-Path $targetDir "xtensa-esp32s3-espidf/release"
espflash save-image --chip esp32s3 --format esp-idf --flash-size 4mb `
    --partition-table partitions.csv --target-app-partition ota_0 `
    "$releaseDir/esp32-rust-ota-client" "$releaseDir/firmware-ota.bin"
Get-FileHash "$releaseDir/firmware-ota.bin" -Algorithm SHA256
```

Do not add `--merge` for OTA. Each supplied OTA slot holds `0x1e0000` (1,966,080)
bytes. A build with missing or test Wi-Fi settings only checks compilation; it
does not verify Wi-Fi, OTA transfer, reboot, or rollback on real hardware.

## Application lifecycle

The runtime calls the selected application's plain `setup` and `main` functions.
On the first boot of an unverified OTA image, a failed `setup` rejects that slot
and requests rollback. Successful setup marks the image valid before the runtime
starts the OTA supervisor and calls the long-running application `main` function.
Put fallible peripheral construction and startup checks in `setup`.

The Wi-Fi manager owns the modem, event loop, and NVS-backed ESP Wi-Fi service.
Applications receive a read-only network state handle and a bundle of available
ESP32-S3 application peripherals through `AppContext`. They must not call
`Peripherals::take()` themselves.

## Managed upload examples

- `../uploaded-firmware-basic` is the minimal ZIP-ready application.
- `../uploaded-firmware-with-libs` demonstrates `heapless`, `serde`, and
  `serde_json` dependencies.

Keep `Cargo.toml`, `ota-app.toml`, and `src/main.rs` at the ZIP root. The server patches
the declared `firmware-app-api` placeholder only in its generated build copy.

## Partitions and rollback

The supplied 4 MiB example has `nvs`, `otadata`, `phy_init`, `ota_0`, and
`ota_1`. ESP-IDF selects the inactive OTA slot; the client streams in 4 KiB chunks
and verifies SHA-256 before activation.

`sdkconfig.defaults` enables application rollback. Test rollback on physical
hardware. SHA-256 provides transfer integrity, not publisher authentication;
production devices should add HTTPS, Secure Boot, and authenticated image signing.
